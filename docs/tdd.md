# TDD 测试驱动开发规范

TDD 是本项目关键业务逻辑的默认开发方式。不是所有改动都必须机械化 TDD，但涉及领域规则、应用服务、安全、幂等、一致性和 API 契约时必须采用 TDD。

## 强制 TDD 范围

以下改动必须先写失败测试，再写实现：

- 考试状态机
- 自动保存
- 手动提交
- 超时提交
- 重复提交幂等
- 答卷锁定
- 权限校验
- 成绩发布
- 异常映射
- API 契约
- 数据库迁移后的仓储行为
- 安全缺陷修复
- 生产缺陷修复

## 可不强制 TDD 的范围

以下改动可以先实现，再补必要验证：

- 文案调整
- 纯样式调整
- 文档修订
- 构建脚本的小范围修正
- 无业务分支的配置变更

## Red-Green-Refactor 循环

每个强制 TDD 任务按以下循环执行：

```text
Red      -> 写一个能失败的测试，失败原因必须对应目标行为
Green    -> 写最小实现，让测试通过
Refactor -> 在测试保护下重构，保持测试通过
Gate     -> 运行质量门禁
```

## 测试命名要求

测试名必须表达业务行为，而不是实现细节。

推荐：

```text
提交后答卷不能继续自动保存
重复提交使用同一个幂等键会返回同一业务结果
考生不能访问未分配考试
```

不推荐：

```text
test method works
service returns true
controller test 1
```

## Bug 修复规则

修复缺陷前必须先补回归测试：

```text
复现失败 -> 写回归测试 -> 修复 -> 验证测试通过
```

不允许直接修复后不留测试。

## Agent 执行要求

Agent 在开始任务前必须判断任务是否属于强制 TDD 范围，并在任务计划中记录：

- 是否需要 TDD
- 先写哪些测试
- 预期失败原因
- 完成后运行哪些门禁
