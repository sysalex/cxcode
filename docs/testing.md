# 测试策略

## TDD 要求

关键业务逻辑必须遵守 `docs/tdd.md`：

```text
先写失败测试 -> 实现最小代码 -> 测试通过 -> 重构 -> 运行质量门禁
```

强制 TDD 范围包括领域规则、应用服务、安全、幂等、一致性、API 契约和缺陷修复。

## 测试分层

- 领域单元测试：业务不变量、策略、状态流转。
- 应用服务测试：用例流程和事务行为。
- Repository 集成测试：数据库映射和 migration 兼容性。
- API 契约测试：请求、响应、状态码、错误码和幂等性。
- E2E 测试：浏览器端完整流程。
- 安全测试：认证、授权和数据隔离。
- 可靠性测试：重试、超时、刷新、网络异常。
- 性能测试：并发考试和自动保存压力。

## 关键场景

生产前必须覆盖：

- 考生登录并打开被分配考试。
- 考生不能打开未分配考试。
- 考试未到开始时间不能进入。
- 浏览器刷新后恢复作答。
- 自动保存能持久化答案。
- 自动保存重试具备幂等性。
- 手动提交会最终锁定答卷。
- 重复提交返回相同业务结果。
- 超时提交会最终锁定答卷。
- 手动提交和超时提交并发时安全收敛。
- 已提交答案不能被编辑。
- 教师可以批改已提交答卷。
- 考生不能查看未发布成绩。
- 考生只能查看自己的已发布成绩。
- 教师不能修改不可变试题版本。

## E2E 约定

前端 E2E 使用 Playwright，并配置为使用本机 Google Chrome：

```text
pnpm --filter @cxcode/web test:e2e
```

Playwright 测试文件使用 `*.e2e.ts` 命名，避免被 Vitest 单元测试收集。

第一条核心 E2E 覆盖：

- 加载考试列表
- 开始作答
- 填写单选题
- 填写简答题
- 手动保存
- 手动交卷
- 交卷后禁止编辑。

## 测试数据

维护固定 fixture 场景：

- 管理员
- 教师
- 考生
- 监考员
- 已排期考试
- 进行中考试
- 已关闭考试
- 草稿试题
- 已发布试题版本
- 进行中作答
- 已提交答卷
- 已评分结果
- 越权访问
- 超时作答

## 时间与并发

涉及考试时间的测试必须使用可控服务端时钟。涉及提交、自动保存、超时的测试必须覆盖重试或并发竞争。
